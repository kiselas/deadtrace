# Public GitHub cohort, 2026-10

Measurements of the scanner on public Python projects, with every reviewed verdict class and its
reason. The projects are open-source GitHub repositories cloned at pinned commits; none is private.
This is development evidence, not a general precision claim.

## Method

- **Selection.** `gh` repository search per stack (FastAPI, Django, Flask, ASGI frameworks, workers,
  CLI, pytest plugins, libraries, Dishka), licenses MIT/Apache-2.0/BSD, not a fork, pushed within the
  last 12 months, 50 to 30,000 stars, a `pyproject.toml` and a tests directory. Quotas per stack, a
  fixed seed (20261006) and a blind dev/holdout split drawn before any scan: 134 projects (80 dev,
  54 holdout). A second, disjoint cohort of 77 projects (seed 20261007) was drawn later as a fresh
  holdout, because the first holdout's mechanisms drove two model changes (ADR-0050, ADR-0051).
- **Scan.** `deadtrace scan`, no configuration, model revision 31 (first cohort) and 33 (second),
  clean commits. No target code was executed.
- **Verdicts.** At most 8 findings per project, drawn with a fixed seed, each member judged by a
  Sonnet reviewer against the project's source (a use means a call, reference, framework convention,
  resolved string, or documented public API of a library). A finding is true only if all its members
  are. One reviewer judged each row; there was no second opinion.

On the third holdout, `RCH001` was 69 of 164 true (42%) and `RCH004` 7 of 28 (25%). Two blind

## Model 53: blocked findings and the fifth cohort

Revisions 36-53 (ADR-0054 to ADR-0071) were designed on the second, third and fourth cohorts, which
were reviewed and so no longer blind. Two kinds of change moved precision:

- rules that resolve what the model missed: test files named by `pytest` commands and CI workflows,
  unittest parameters and base-class fixtures, a nested package imported by its own name
  (`sys.path.insert`, `packages/*/src`), dotted strings and `INSTALLED_APPS` through it, scripts
  without a main guard, files that tools run (`noxfile.py`, `setup.py`, `docs/conf.py`, mkdocs
  hooks), and Poetry, flit and `setup.cfg` entry points;
- *blocked findings* (ADR-0071): RCH001 and RCH004 findings of four forms that review showed to be
  mostly false are held back with a reason instead of shown. On the reviewed findings of cohorts b-d:
  methods of classes with an external base were 20% true, code under examples/docs/scripts/tools
  27%, documented or `__all__` public API of a package 35%, names mentioned in configuration files
  32%. No other structural slice of the findings was above 71%.

On the fifth cohort, drawn after these changes and scanned once at model 53, 104 of 159 reviewed
findings from 29 projects were true: **65.4%** (95% Wilson interval 57.7-72.4). By code: `RCH001`
78 of 111 (70.3%), `RCH004` 25 of 31 (80.6%), `RCH002` 1 of 17 (5.9%). RCH002 failed where routers
are mounted inside an application factory through a registry, by a router that is itself mounted
conditionally, or after an import inside the assembling function; model 54 (ADR-0072) addresses those
three forms. On the same findings, now reviewed and so not blind, model 54 removed 16 false findings
(all RCH002) and no true one: 104 of 143 still reported are true (72.7%).

## Model 59: the sixth cohort

Revisions 55-59 (ADR-0073 to ADR-0076) were designed on the reviewed cohorts b-e: a self call reaches a
mixin's member through each subclass's MRO, hooks are blocked across the class hierarchy for public
names, instances in a literal options dict passed to a library keep their methods, and names called
in docstring examples count under `--doctest-modules`. On the sixth cohort, drawn after them and
scanned once at model 59, 87 of 129 reviewed findings from 26 projects were true: **67.4%** (95%
Wilson interval 59.0-74.9). By code: `RCH001` 79 of 117 (67.5%), `RCH004` 6 of 7, `RCH002` 2 of 5.
The fifth and sixth cohorts agree within their intervals: precision of this alpha is about two thirds.
Model 61 (ADR-0077, ADR-0078) then removed 9 false findings of the sixth cohort and no true one
(72.5%, not blind): routers of modules imported inside the assembling function, and sibling modules
imported by bare name after a script edits `sys.path`.

One project of the sixth cohort (1,489 files) exhausted the measuring tool's memory, not the
analyzer's: deadtrace finished it in under eight minutes with no findings. The tool is fixed.

## Model 75: the seventh cohort

Revisions 62-75 (ADR-0076 and ADR-0080 to ADR-0092) were designed on the reviewed cohorts b-f and on
the recall injections. The largest changes: a subscripted base such as `BaseRepo[User]` is the
project class (it used to count as an external base whose hooks protect every method); a class
handed to an unknown consumer exposes its public methods, not its private ones; and `getattr` on a
value of unknown type no longer protects the whole program when its name is known, or when the
project keeps no module as a value. Before these, 80 of 362 cohort projects had such a whole-program
guard, and 73 of them reported nothing; at model 71, 55 had it.

The findings these revisions added to cohorts b-f were reviewed separately (99 sampled findings,
51.5% true at model 71). Revisions 72-75 removed 24 of their false findings and no true one (68.0%
at model 75, not blind): reflection over a class namespace, metaclass methods that call members of
the classes they build, modules imported inside a fixture and returned, and a listing of an unknown
value's members restricted to public ones.

On the seventh cohort, drawn before these revisions (seed 20261018, 81 projects) and scanned once at
model 75, 100 of 140 reviewed findings from 29 projects were true: **71.4%** (95% Wilson interval
63.5-78.3). By code: `RCH001` 84 of 121 (69.4%), `RCH004` 16 of 19 (84.2%). Three blind cohorts now
read 65.4%, 67.4% and 71.4%. The leading false classes are classes used only as type arguments in
annotations of nested test code, modules loaded by computed names, and Django models that only the
app registry uses.

## Model 88: the eighth cohort

Revisions 76-88 (ADR-0093 to ADR-0105) were designed on the reviewed cohorts b-g, the seventh among
them once its review was done. On those cohorts at model 81, not blind, 366 of 471 reviewed findings
of b-f were true (77.7%) and 97 of 121 of g (80.2%). The later revisions add two blocked reasons:
stub methods that subclasses override (`interface_declaration`), and type checker inputs under test
directories (`type_check_input`).

The eighth cohort was drawn before these revisions were measured (seed 20261021, 88 projects; the
top search results were used up by earlier cohorts, so the search went six pages deep instead of
two) and scanned once at model 88. 124 of 169 reviewed findings from 34 projects were true:
**73.4%** (95% Wilson interval 66.2-79.5). By code: `RCH001` 101 of 124 (81.5%), `RCH004` 23 of 31
(74.2%), and `RCH002` none of 14: this cohort had many FastAPI projects that mount routers in a loop
over modules or over a list of module names, which the router model does not follow. `RCH001` and
`RCH004` together were 124 of 155 (80.0%, 73.0-85.5).

### Development comparisons after model 88

Revisions 89–93 were evaluated sequentially on the same pinned sources of 531 previously
reviewed development targets from cohorts b–h. These cohorts were used for changes and are
not blind. The two previously excluded targets remain excluded. Runs used Python 3.12.4
and exact clean revision commits; concurrent workers were used only for finding comparisons,
not performance claims.

| Comparison | New findings | Removed confirmed false | Removed confirmed true | Removed unreviewed |
| --- | ---: | ---: | ---: | ---: |
| Model 88 → 92 | 0 | 21 | 4 | 18 |
| Model 92 → 93 | 0 | 2 | 0 | 0 |

The four true findings lost at model 90 remain classified as true: optional known-name getattr
dispatch conservatively protects test stand-ins even when the tested path does not call that
method. The unchanged injection results do not erase this loss on real reviewed code.
Model 93 fixes two inherited Django fixture hooks; two callbacks on alternative conditional
class definitions remain unresolved. Neither comparison is a new blind accuracy estimate.

Seed-7 injections were compared by exact target sets, injection identities and reported flags,
which are unchanged: 534/721 development and 964/1,565 holdout. Reported incomplete worlds were
kept distinct from crashes and timeouts; all compared runs completed without operational errors.

### Model 94: local Cookiecutter extensions

Model 94 (ADR-0119) adds conservative roots for local extension objects explicitly
listed in a template's `cookiecutter.json`. On the same pinned sources and configuration
digests of all 531 active projects in reviewed development cohorts b-h, compared with
model 93, it added no finding and removed one previously reviewed false finding: a
manifest-selected filter in a FastAPI template. No true, unsure or unverified finding
was removed. All runs completed without operational errors; each project's completeness
flag was unchanged, including worlds that remain incomplete.

Exact seed-7 injection identities and reported flags were unchanged at 534/721 development
and 964/1,565 held-out packages. The new independent case failed four expectations on
model 93 and passes on model 94, while its three unused controls remain candidates.
These are paired development results, not a fresh blind precision estimate. No target
code was imported or executed. Parallel quality scans were not performance measurements.

### Comparison with vulture

Vulture 2.16 (default confidence 60) ran on the pinned sources of cohorts b, c and d (224 projects).
Only functions, methods, classes and properties were kept, the kinds deadtrace reports. Two of its
findings per project were reviewed with the same instructions (vulture claims a definition is unused
anywhere, so a use in tests makes its finding false).

| Tool | Reviewed | True | Precision (95% CI) | Findings shown on the 224 projects |
| --- | ---: | ---: | --- | ---: |
| deadtrace, model 53 | 266 | 178 | 66.9% (61.1-72.3) | 809 findings, 1,315 definitions |
| vulture 2.16 | 417 | 66 | 15.8% (12.6-19.6) | 25,572 definitions |

The deadtrace row is **not** blind: revisions 36-53 were designed on these cohorts. The blind
figure is the fifth cohort's. Vulture's false findings were mostly decorator registration (routes,
tasks, signal handlers; 133 rows), hooks of framework base classes (56), pytest autouse fixtures and
plugin hooks (about 33), and library public API (about 30).

## Why findings were false

Largest classes on the second holdout (reviewed members, not findings):

| Mechanism | Members | Note |
| --- | ---: | --- |
| `unittest discover` default pattern `test*.py` matches `tests_*.py` | 56 | one project's runner script |
| public API of a library (exported, documented, or both) | about 70 | judgement-dependent: what is public API of a library |
| plain call, URLconf or string reference not resolved | 17 | |
| test classes collected by a runner other than pytest | 12 | |
| conventions of external base classes | 8 | |
| tests run by explicit path through `pytester` | 8 | |

Largest classes on the third holdout: test modules that do not match `test_*.py` but are run by
an explicit path in a Makefile or CI (`pytest tests.py`), 154 members, mostly two projects; a
module imported from a string a runner snippet executes, 62; subpackage `__all__` exports of an
installed package counted as public API, 32; `app:function` references in supervisor and launcher
configuration, 23; modules named in strings and loaded by a plugin loader, 21; conventions of
external base classes, 15; a unittest base re-exported by a sibling module, 15.

The first holdout showed `django.test.TestCase` subclasses (about 140 members) and a Flask
application built in a test fixture hiding a library's API (37 members); both are fixed in
revisions 32 and 33 and no longer appear.

## What this does and does not show

- Precision was about half before model 53 and about two thirds after it, so findings still need
  review before deletion, as the report says. The sample favours projects with many findings (at most 8 per project) and a reviewer who
  counts documented library API as a use; stricter or looser reading changes the number.
- No scan crashed on 287 projects, and 46 of 287 had a world that could not be completed, 36 of
  them because a pytest fixture or parametrization could not be resolved.
- A true verdict means no use was found by reading, not that deletion was tested.
