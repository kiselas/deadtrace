# Deadtrace Development Roadmap

Status date: 2026-09-26. This is the canonical execution roadmap kept with the code. Decision
records live in `docs/adr/`; the analysis contract and architecture notes are pending there as
well. This file defines what to build next, in what order, and what evidence is required before a
task may be marked done.

Deadtrace is a static, explainable dead-code analyzer. The immediate product is a dependable
read-only tool for Python 3.12 applications using FastAPI, Dishka, Pydantic, pytest, and nearby
integration patterns. Broader frameworks, evidence import, patch preview, verification, and other
languages are gated extensions—not shortcuts around proving the primary workflow.

PyPI publication is explicitly out of scope until the owner requests it.

## Status vocabulary

- **implemented**: code and regression evidence exist locally;
- **verified**: the complete repository gate and the relevant artifact/oracle pass;
- **accepted**: required field evidence and human review also exist;
- **blocked**: an external input is required and no safe repository work can advance that item;
- **deferred**: its documented entry gate has not been met.

Passing a synthetic fixture is not field acceptance. A limitation or conservative guard is a valid
safety outcome, but it is not modeled coverage. A finding always means “review under these inputs,”
never “safe to delete.”

The scale fixture is generated by `benchmarks/generate_scale_fixture.py`. It holds one function per
module and produces no edges, classes, imports, or framework objects, so it measures parsing only
and cannot on its own show that the budget is met; PERF-00 below adds the service fixture and real
sources. On the 2026-09-21 baseline, median stage times on the scale fixture over three
fresh-process runs, with the sub-stages that carry them, were:

```text
collect    7.608 s   inventory metadata 6.181, inventory parse 1.286, discovery+read+verify 0.161
frontend  18.044 s   symbols 6.535, frameworks 6.185, imports 2.912, flow 1.541, parse 1.108
solve      0.002 s
total     25.654 s
```

That profile put 85.0% of wall time into five per-module LibCST `MetadataWrapper`/`PositionProvider`
passes and 0.6% into file collection (`benchmarks/results/2026-09-21-scale-50k-baseline.md`), which
made performance the first repository-owned release blocker. ADR-0004, ADR-0005, and ADR-0007
brought both 50k fixtures to 0.6–1.3 seconds with byte-identical reports
(`benchmarks/results/2026-09-24-stdlib-ast.md`).

## Non-negotiable invariants

Every work package must preserve these rules:

1. Ordinary scan never imports, executes, installs, or connects target code.
2. Source universe, report visibility, external contracts, and test worlds remain distinct.
3. Resolved execution, conservative execution, declaration retention, and unknown boundaries are
   separate facts with derivations.
4. Missing roots, invalid assembly, incompatible versions, and unresolved selection cannot create
   stronger negative findings.
5. State is world-local; tests, applications, and containers do not leak facts into one another.
6. Baselines and filters never alter the graph or hide operational/model blockers.
7. Reports are deterministic for the same source/config/model/target descriptors.
8. Semantic changes increment `MODEL_REVISION` and update corpus expectations and support claims.
9. No feature may satisfy acceptance by turning the entire project into unknown.
10. No automatic source mutation is added before the preview and verification gates below.

The A01–A40 identifiers used below refer to an acceptance traceability map that has not been
published yet; it is planned as `docs/acceptance-matrix.md` (see ADR-0001). Until then they are
stable labels without repository definitions.

## Critical path

```text
P0 performance gate
  → P1 oracle and metamorphic hardening
  → P2 pilot kit
  → P3 authorized real-project pilot and triage
  → P4 blocker-driven FastAPI/Dishka improvements
  → P5 read-only alpha release gate
  → P6 repeatable beta workflow on two projects
  → evidence / preview / verification tracks only when their entry gates are met
```

P0, P1, and most of P2 can run without private project access. P3 cannot be replaced by another
synthetic repository. P3 must not start while `fixtures/known-violations` lists unmet targets for
plain Python code: a pilot would spend its review budget on candidates the contract already
forbids. After SOUND-01 the list is empty.

## P0 — meet the 50k-LOC performance budget

Priority: **P0 / next**. Recommended assignment for the additional agent.

### PERF-00 — measure on framework-shaped and real code

**Status:** implemented on 2026-09-24: `benchmarks/generate_service_fixture.py` and
`benchmarks/stage_installed_sources.py`; evidence in
`benchmarks/results/2026-09-24-indexed-lookups.md`.

The budget applies to the 50,000-line service fixture as well as to the scale fixture. The service
fixture repeats a FastAPI/Dishka/Pydantic domain package, so its cost grows with symbols, calls,
routes, and bindings; on it, `main` showed quadratic growth in framework discovery, planning, and
finding construction that the scale fixture could not reveal. Installed third-party sources give
real code up to 129k lines. None of these inputs is precision evidence.

### PERF-01 — profile without changing semantics

**Status:** implemented on 2026-09-21 (`deadtrace.timing`, benchmark artifact schema 2, ADR-0003);
evidence in `benchmarks/results/2026-09-21-scale-50k-baseline.md`. Verification and acceptance per
the status vocabulary remain open.

Owner files:

- `src/deadtrace/scanner.py`
- `src/deadtrace/python_frontend.py`
- `src/deadtrace/frameworks.py`
- `src/deadtrace/benchmark.py`
- `benchmarks/`
- new focused performance tests

Work:

- add bounded sub-stage counters/timings sufficient to separate discovery, stable snapshot reads,
  CST parsing/metadata, symbol collection, import resolution, flow extraction, framework modeling,
  finding construction, and reporting;
- record platform, Python version, Deadtrace version/model revision, files, LOC, nodes, edges, worlds,
  and process peak RSS in benchmark artifacts without usernames or project source;
- produce a profile of the deterministic 50k fixture before optimizing;
- do not use `tracemalloc` in timed runs; it materially distorts this workload.

Acceptance:

- benchmark artifact remains deterministic except documented volatile measurements;
- stage totals are internally consistent and tested;
- no target execution or source content enters the artifact.

### PERF-02 — optimize source collection

Current baseline: 7.608 seconds for 251 Python files totaling about 0.75 MB, of which discovery,
reading, hashing, and snapshot verification take 0.161 seconds. The remainder is the inventory's own
LibCST parse and metadata pass (`collect.inventory_parse`, `collect.inventory_visit`), so the
acceptance criterion below should be re-stated against the sub-stage numbers before work starts.

Investigate measured costs such as repeated path resolution, directory walks, stable-snapshot
verification, decoding, hashing, and duplicate parsing. Preserve A30/A38/A39: symlink escape,
encoding/read errors, no side effects, and whole-snapshot retry must remain safe.

Acceptance:

- the source/config/model digests and semantic report for every existing corpus case are unchanged;
- repeated file mutation still yields retry or `DT1002`, never a mixed semantic snapshot;
- collection on the 50k fixture is at most 5 seconds on the recorded Windows host.

### PERF-03 — optimize frontend/model construction

**Status:** first lever implemented on 2026-09-24 (ADR-0004): one parse and one position pass
per module, shared by inventory, frontend, and framework discovery. Same-session medians on
the 50k fixture: 36.005 s on `main`, 13.242 s with the change, reports byte-identical; see
`benchmarks/results/2026-09-24-scale-50k-single-parse.md`.

Second lever (PERF-03b) implemented on 2026-09-24 (ADR-0005): symbol, member, object,
registration, container-binding, and adjacency lookups use indexes built once per analysis, and
each called function's body is walked once instead of once per call site. On the 50k service
fixture the affected stages fall from 15.9 to 2.2 seconds at the median and stop growing faster
than the source; reports are byte-identical. Verification and acceptance remain open.

Third lever (FRONTEND-02) implemented on 2026-09-24 (ADR-0007): the analysis parses with the
standard-library `ast` module, and LibCST is no longer a dependency. In alternating runs the 50k
scale fixture takes 0.61 instead of 11.75 seconds, the 50k service fixture 1.23 instead of 16.31,
and mypy's 129k lines 2.58 instead of 65.78; peak RSS falls to 84, 141, and 256 MiB. Reports are
byte-identical and a canonical dump of every parser-independent fact is identical for 51 targets;
see `benchmarks/results/2026-09-24-stdlib-ast.md`. The time and RSS budget is met on the recorded
host for both 50k fixtures; verification waits for PERF-04 on CI runners.

Memory now grows by about 2 MiB per 1,000 lines because every module's syntax tree lives until the
frontend finishes. The next lever is extracting compact per-module facts and releasing each tree
afterwards, which also makes per-file caching and parallel parsing possible.

Current baseline: 18.044 seconds; solver time is not the bottleneck. Measured sub-stages put 15.631
seconds of the frontend into per-module LibCST `MetadataWrapper`/`PositionProvider` passes (and
another 6.181 seconds into the same work inside the inventory), 1.108 seconds into parsing, and
1.541 seconds into flow extraction.

Use the profile to remove repeated CST metadata work, redundant traversals, avoidable quadratic
lookups, and duplicate normalization. Prefer indexed immutable facts over caches with unclear
invalidation. Do not weaken descriptors, guards, definition-time effects, or framework discovery.

Acceptance:

- all A01–A40 and semantic manifests remain unchanged unless an independently justified bug is
  found and documented;
- complete 50k cold scan is below 30 seconds and process peak RSS below 1 GiB;
- run three fresh-process measurements and commit the host descriptor plus raw JSON artifacts;
- cold and immediate repeated results have identical canonical semantic output.

### PERF-04 — CI performance guard

**Status:** manual workflow implemented on 2026-09-24 (`.github/workflows/performance.yml`,
`benchmarks/check_budget.py`). Promotion to scheduled or required waits for measured runner
variance. First hosted run, three runs per fixture: the scale fixture 0.85 seconds on Linux and
1.60 on Windows, the service fixture 2.33 and 2.60, peak RSS 131 to 193 MiB.

Add a manually dispatchable workflow first. Promote it to scheduled/required only after runner
variance is measured. The workflow generates the scale and service fixtures, runs from a built
wheel, uploads the JSON artifacts, and fails on the agreed time/RSS thresholds. It must not commit
the generated projects.

## P1 — oracle, paired, and metamorphic hardening

Priority: **P0 before field claims**. This lane can run in parallel with performance work if it
touches only `tests/oracle/`, `corpus/`, and new test modules.

### SOUND-00 — record present contract violations

**Status:** implemented on 2026-09-24 (ADR-0006). Eight cases under `fixtures/known-violations`
record complete worlds that report code that may run: registry and returned-reference calls, base
classes and inherited methods, overrides called through a base-class annotation, methods on an
untyped receiver, Celery-decorated tasks, and the seed `escaped-callback-helper` with a configured
world. `tests/test_known_violations.py` pins the twelve unmet targets.

### SOUND-01 — meet the recorded expectations

**Status:** implemented on 2026-09-24 (ADR-0008, model revision 5): references, members and
owners, bases and method resolution order, `super()`, class hierarchy dispatch, unknown
receivers, decorators, evaluated annotations, Python scoping, and model-level Pydantic hooks.
A second probe added five cases before the fix; all thirteen are met and moved to `corpus/`.

Priority: **before P3**. Fix the Python-core cases in the frontend and solver, one bounded pattern at
a time, each with a model revision bump, the case moved to `corpus/` with its `[analysis]` table,
and the pinned list shortened. Precise modeling and conservative protection are both acceptable
where the case says so; weakening a whole world is not, where the case has a control candidate.
Unmodeled-framework registrations (the Celery cases) need a guard that is local to the decorated
function or an explicit world limitation.

### SOUND-02 — implicit dispatch and names in strings

**Status:** implemented on 2026-09-24 (ADR-0009, model revision 6): special methods, hooks
of external base classes, modules and symbols named by strings, dynamic imports, and `DT2002`
only for boundaries that protect something. Four cases were recorded first and moved to
`corpus/`.

### SOUND-03 — module execution

**Status:** implemented on 2026-09-24 (ADR-0010, model revision 7): imports run modules
wherever they execute, packages run before their modules, and star imports, package
re-exports, function-level imports, and alternative bindings resolve. Six cases were
recorded first and moved to `corpus/`.

### ROOTS-01 — automatic worlds for any project

**Status:** implemented on 2026-09-24 (ADR-0011, model revision 8): scripts and
`__main__` modules, applications and factories of ten frameworks without a capability,
uncalled FastAPI factories, Celery task autodiscovery, a library world for projects
without applications, and a solver budget sized from the graph. Library worlds on rich
and pygments exposed four core-model violations, fixed by SOUND-04.

### SOUND-04 — overloads, library hooks, and escaped classes

**Status:** implemented on 2026-09-24 (ADR-0012, model revision 9): `@overload`
signatures live with their implementation, single-underscore hooks are protected, a nested
function bound in one branch is reachable, and classes that escape expose their methods
unless a capability models the consumer. rich and pygments now report only dead code.

### DJANGO-01 — installed applications

**Status:** implemented on 2026-09-24 (ADR-0013, model revision 10): settings modules are
application roots; installed applications' packages, `apps`, `models`, `admin`, template-tag
libraries, and management commands are imported, model classes registered, and `Command`
classes instantiated; strings may name a module attribute such as `WSGI_APPLICATION`. URL
patterns, admin classes, and signal receivers stay under the general conservative rules.

### FIELD-01 — first zero-configuration field audit

**Status:** implemented on 2026-09-26 (ADR-0015, ADR-0016, ADR-0017, model revision 11). Six
local checkouts — a FastAPI and Dishka service of 108k lines, two smaller FastAPI services, a
Django, Django REST framework, and Celery service, two pytest-based automation projects — and
Deadtrace itself were scanned without configuration and every finding was checked against the
source. Before: environments were scanned as project code (341 seconds on one checkout), the
tests world was partial on every project, and all 25 `RCH002` findings on the service were false.
After: every audited world that can be complete is, and each remaining finding was confirmed as
code that does not run under the analyzed inputs. This is private field evidence without
recorded source; it is not the P3 pilot, which needs labeled review groups.

### FIELD-02 — second field pass

**Status:** implemented on 2026-09-26 (ADR-0018, model revision 12): supported FastAPI and
Dishka version ranges, source `exclude`, test stand-ins, run-time fixture requests, `pytest11`
exports, Typer and Click commands, and solver and pytest-model costs on a 624k-line monorepo.
Memory on such a monorepo, about 2.2 GiB, remains the next lever (PERF-03).

### FIELD-03 — third field pass

**Status:** implemented on 2026-09-26 (ADR-0019, model revision 13): wrapped FastAPI factories,

### ORACLE-01 — capability-to-oracle inventory

Create a machine-readable manifest mapping every capability marked `modeled` to:

- applicable target versions;
- positive, negative, and unknown static cases;
- runtime oracle coverage, or an explicit reason why runtime execution is not the right oracle;
- support-matrix wording.

Do not count a static-analysis assertion as runtime evidence for framework behavior.

### ORACLE-02 — FastAPI oracle matrix

Add trusted, pinned runtime tests for the supported subset:

- app/router/operation and nested `Depends` dependencies;
- included versus unpublished routers;
- lifespan startup/cleanup;
- background callbacks;
- selected exception/middleware hooks that are currently claimed as modeled;
- Pydantic hooks used by request/response schema construction.

Each runtime case has an independent static manifest. Scanner output must not be used to manufacture
the oracle expectation.

### ORACLE-03 — Dishka oracle matrix

Add trusted runtime tests for:

- method and class providers, aliases, and constructor selection;
- `from_context`/Request boundaries;
- APP and REQUEST scopes;
- generator cleanup;
- `@inject`, `DishkaRoute`, and multiple isolated containers/apps.

Conditional activation, components, decorators, and `provide_all` remain guarded until a bounded
selection model and versioned oracle exist.

### META-01 — paired and metamorphic suite

Add tests proving:

- reordering files/facts does not change semantic states;
- adding uncertainty cannot strengthen negative output;
- removing the final call in a fresh snapshot removes stale reachability;
- disabling a framework model weakens knowledge rather than creating candidates;
- comments/formatting do not change finding identity;
- cold/repeated scans produce byte-identical canonical reports;
- report truncation changes presentation only.

Existing unit tests cover several rows; this task adds a named suite and closes the missing model
ablation and cold/repeated equivalence cases.

## P2 — reproducible pilot kit

Priority: **P1 after P0/P1 canaries are green**. Does not require pilot source.

### PILOT-01 — manifest and triage schemas

Add versioned, source-free templates and validators for:

- snapshot identifier/commit, dirty state, authorization note;
- scan path, config digest, model revision, target versions, worlds, and source digest;
- setup time, scan stages, RSS, findings selected for review, and limitations;
- per-member labels: true candidate, live/model miss, external contract, input gap, unsupported
  framework mechanism, grouping issue, or unclear;
- decision memo and minimized-regression reference.

Private source, secrets, object values, and proprietary snippets are excluded by default.

### PILOT-02 — one-command read-only capture

Provide a documented command sequence that produces semantic report, doctor output, benchmark, and
privacy-conscious support bundle from the same immutable source/config/model descriptors. It must
detect descriptor drift between artifacts and never run target code.

### PILOT-03 — review protocol

Document sampling and labeling rules so results are not cherry-picked. Required minimum for PR-08
acceptance remains 30 independently reviewed groups across three suitable snapshots, with unresolved
items counted separately.

## P3 — authorized real-project pilot

Priority: **externally gated**.

Required input from the owner:

- authorized repository/path and fixed commit or immutable snapshot;
- intended production/test scenarios and application roots;
- exact FastAPI/Dishka/Python versions and supported commands;
- permission boundary for derived minimal regressions;
- a human able to label the first review groups.

Deliverables:

- completed pilot manifest and reproducible reports;
- per-member triage, not only group-level labels;
- ranked blocker list split into Python flow, framework model, missing input, version mismatch,
  genuine dynamics, grouping, and UX;
- decision: continue, narrow scope, repair foundations, or stop a capability claim.

Acceptance requires useful decisions, not a target precision percentage manufactured from one
project. This package is **blocked on external pilot input** until such a snapshot is supplied.

## P4 — blocker-driven FastAPI/Dishka depth

Only start capabilities demonstrated by P3 or repeated user reports. Each item requires a minimal
case, exact/guarded behavior, version applicability, oracle, before/after pilot evidence, and a
model revision bump.

Candidate backlog, ordered by likely relevance but not pre-approved:

1. additional bounded app/container factory shapes and late registration order;
2. Dishka components/decorators/conditional selection slices;
3. finite string/callable registries and known wrappers;
4. additional FastAPI middleware, exception, WebSocket, and dependency override patterns;
5. SQLAlchemy/Pydantic lifecycle retention needed by FastAPI services;
6. pytest plugin adapters selected from actual test-world blockers.

Do not launch full Django, Celery, ORM, CLI, and multi-language support in parallel.

## P5 — read-only alpha release gate

Publication remains a separate owner action. Before tagging an alpha candidate:

- P0 performance budget passes or the owner explicitly narrows supported project size with measured
  limits;
- P1 oracle/corpus matrix covers every claimed modeled capability;
- P3 field pilot and minimum triage exist;
- no known unfixed must-preserve or analysis-contract violation remains;
- schema 1, config, model and capability revisions are documented;
- source provenance/licensing review, changelog, support matrix, limitations, and quickstart agree;
- wheel/sdist are rebuilt reproducibly and smoke-tested on Windows and Linux outside the checkout;
- release notes include exact commands, versions, skips, performance host, and open limitations.

## P6 — beta workflow for repeated CI use

Already implemented: saved-report comparison, three comparability states, source/limitation deltas,
baseline create/update with explicit acceptance, CI exit policies, static PEP 621 entry-point roots,
and privacy-conscious support bundles.

Remaining work:

- repeat the workflow on two real projects across real source changes;
- define migrations only when a future report/baseline schema actually changes;
- add SARIF only after users request inline findings and location semantics are stable;
- improve automatic roots/lock formats one bounded source at a time;
- prove upgrades produce understandable comparison results instead of mass churn.

Exit: teams can adopt existing debt, fail only on genuinely new comparable findings, and still see
all limitations and stale baseline entries.

## Gated later tracks

### Evidence (future 0.3)

Entry gate: stable beta identities plus user demand. Add provenance-rich evidence records, two-
report lost-reachability analysis, safe local Git blob/tree reading, and one data-only coverage
format. Never use absent coverage as proof of deadness; runtime/static contradictions become model
bugs.

### Patch preview (future 0.4)

Entry gate: field-confirmed candidates and an explicit effect/retention contract. Produce a
snapshot-bound plan and diff only; do not mutate the target. Begin with a tiny allowlist of LibCST
rewrites whose binding/import/declaration effects are proved by fixtures.

### Verification/apply (future 0.5)

Entry gate: accepted preview workflow and a reviewed runner threat model. Target execution belongs
to a separate opt-in isolated runner with baseline/patched runs,
network/credential/filesystem/resource policy, logs, rollback, and explicit user approval. Ordinary
`scan` stays static.

### Stable 1.0 and ecosystem expansion

1.0 requires repeated field value, a stable compatibility/schema policy, predictable performance,
and maintained oracle coverage. Full Django, Celery, CLI registries, ORMs, and additional languages
become separate capability tracks with an owner and pilot. A language-neutral plugin architecture is
considered only after the Python contracts have proved reusable; it must not dilute Python safety.

## Definition of done for every repository task

- the user-visible outcome and non-goals are stated;
- positive, negative, and unknown/guard cases exist where semantics change;
- canonical output is deterministic and saved artifacts validate strictly;
- no target execution, network use, or filesystem mutation is introduced into scan;
- all relevant support/limitation/schema/changelog documents are updated;
- full quality, corpus, wheel, and task-specific gates pass;
- field claims cite field evidence; synthetic tests are labeled as synthetic;
- the task is not marked done while required evidence is missing.
